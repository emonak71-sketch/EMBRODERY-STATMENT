# Embroidery Statement — Safe Worker Management Setup

## Before running SQL

1. Open the existing Supabase project for Embroidery Statement.
2. Open **Database → Backups** and confirm that a recent backup is available. If the project plan does not include downloadable backups, follow the current Supabase CLI backup guide linked below.
3. Remember: Supabase database backups do **not** include Storage API file objects. The current project had no Storage buckets or Storage objects at the time of inspection, but keep any files stored outside Supabase separately.
4. Do not delete, reset, or recreate the Supabase project.

Official backup guide: https://supabase.com/docs/guides/platform/backups

## Apply the additive SQL

1. Open **SQL Editor → New query** in the existing Supabase project.
2. Open `supabase/worker-management-additive.sql` from this branch.
3. Copy the complete SQL into the SQL Editor.
4. Run it once. The script is wrapped in a transaction: if a statement fails, the transaction rolls back.
5. Do not rerun the older `supabase/worker-attendance-payroll.sql` or `supabase-fix.sql` scripts. The existing Worker tables and policies are already present.

The script does not update or delete existing Parties, Transactions, Products, Expenses, Sales, Workers, Attendance or Payroll rows. It creates new worker-document, increment and advance ledgers, adds payroll columns, and creates a private Storage bucket.

It also removes the legacy `auto_confirm_user_trigger` and its function. This does not delete or modify existing accounts. It stops future signups from being silently auto-confirmed, so the existing app's six-digit email OTP flow can work as intended. Confirm that **Authentication → Providers → Email → Confirm email** is enabled before testing a new signup.

## Verify

1. Open `supabase/worker-management-verify.sql`.
2. Run it in SQL Editor. It is read-only.
3. Confirm:
   - Existing account, Parties and Transactions counts are still present.
   - The ownerless legacy Party row is still present and has not been reassigned.
   - The new worker tables exist and have RLS enabled.
   - The `worker-documents` bucket is private.
   - The old auto-confirm trigger is absent.

## Deploy the application code

1. Wait for the GitHub checks on Pull Request #14 to pass.
2. Only after the SQL setup and verification succeed, review and merge the draft PR into `main`.
3. Allow the connected deployment platform to build the updated application.
4. Sign in using the existing account that owns the current business records. Do not create a replacement account to test the data.

## Important operating notes

- Worker IDs are generated by PostgreSQL (for example, `EMP-1001`) and remain unique across accounts.
- New documents are stored in a private bucket; old uploads are not overwritten or deleted.
- Salary increments record the previous salary and new salary; the database checks that the worker's current salary still matches before applying an increment.
- Paying a payroll recovers outstanding advances assigned to that month and earlier unpaid months. Paid payroll rows are locked against financial edits.
- Annual report cash outflow is net salary actually paid plus advances actually disbursed. Advance recovery is shown separately and is not counted a second time.
- The SMS composer prepares a custom message and opens the device's SMS app. Direct automatic SMS gateway delivery still requires a provider account/API credential.
